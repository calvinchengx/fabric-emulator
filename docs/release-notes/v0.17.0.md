# v0.17.0

The release where a consumer's real data product ran its full medallion,
landing to gold, against the emulator unmodified: a DataPipeline entry item, a
21-table bronze fan-out over concurrent notebook runs, a silver upsert layer,
and a 47-step contract-ordered gold build. Every gap that run surfaced is
closed here. Most of them share one shape, and it is the worst shape an
emulator can have: **the run goes green and the data is not where anyone will
look for it.** A wrong answer that raises gets fixed; a right-looking answer
that silently lands in the wrong place ships.

No breaking API changes. Two behaviours move in the stricter direction and are
called out below.

---

## Read this one first: schema-qualified writes landed outside the lakehouse

Fabric's schema-enabled lakehouses nest tables one level down
(`Tables/<schema>/<table>`). The catalog reflection did not model that layout
at all, so `saveAsTable("bronze.x")` needed a schema that either did not exist
or, created bare, lived in the engine's own warehouse. The write then
succeeded, reported its row counts, and left **nothing in OneLake**. The same
consumer run found the CTAS variant weeks of commits later: 47
`CREATE OR REPLACE TABLE gold.x AS SELECT` statements went green with an empty
lakehouse behind them.

Both directions are closed:

- Session bind now reflects schema folders into the engine catalog WITH their
  OneLake locations. A folder under `Tables/` whose immediate children carry no
  `_delta_log` registers as a schema; its Delta children register
  schema-qualified; an EMPTY schema folder registers too, because that is what
  a provisioned schema looks like before its first write. The old first-level
  contract is untouched and pinned by the pre-existing tests: a first-level
  folder is a table unless the evidence says otherwise.
- CTAS naming a schema the emulator registered runs its SELECT on the engine
  and lands the write at `<schema-location>/<table>`, then registers the
  result. CTAS into a schema nobody gave a location keeps the engine's own
  placement, which is then the right answer.

**Stricter, on purpose:** a write into a schema that does not exist now fails
the way it fails on Fabric. The emulator reflects provisioned state; it does
not invent it.

## MERGE INTO fails on any temporal-columned target

Sail parses `MERGE INTO` and then fails plan resolution against any Delta
target holding a date or timestamp column:

```
attribute ObjectName([Identifier("#0")]) is missing from the schema
```

Reproduced minimally (a two-column table plus one DATE column) and unchanged
in pysail 0.7.0. Audit-columned tables are the norm, so in practice every
upsert notebook was unrunnable.

A bounded MERGE grammar (equality join, `UPDATE SET` and `INSERT` branches, a
bare view or table as source) now routes through delta-rs, the same path
OPTIMIZE and VACUUM have always taken: the source is materialised from the
session via Arrow so the temporal types survive, the upsert happens against
the same table, and the metrics come back as a result row. Anything the
grammar does not understand falls through to the engine untouched, honest
failure included. Backtick identifiers are rewritten to DataFusion's double
quotes, which also keeps case-sensitive column names resolvable.

## `input_file_name()` reconstructed, not stubbed

Sail rejects the function outright, and it fails at write time, long after the
read looked fine. The tempting fix, a UDF returning `""`, would write wrong
lineage for every row; that is the "looks like support and provides none"
defect this project keeps refusing.

Instead the agent, only when the engine probe shows the function missing,
wraps the file readers to expand a glob via the OneLake DFS listing, reads
each file with its own path stamped on its rows, unions the parts, and rebinds
`F.input_file_name` to resolve to that stamp. `DataFrame.write` drops the
bookkeeping column, so persisted tables stay schema-identical to Fabric.
Every row genuinely carries the file it came from. The JVM overlay keeps
Spark's native implementation; the shim declines to install where the engine
has the real thing.

Known bounds, stated rather than hidden: SQL-string usage
(`spark.sql("SELECT input_file_name() ...")`) bypasses the rebind, and calling
it on a frame that never came from a file read errors where Spark returns
`""`.

## Concurrent notebook runs corrupted each other's exit status

The prelude runs once per session, and each run re-pointed the one shared
`notebookutils` module's `exit` at its own copy of `notebook_exit`, whose
`global __nb_exit__` wrote into whichever session ran its prelude LAST. Under
a 21-way concurrent fan-out most SUCCESS exits were recorded Failed, because
the exit value landed in another session's namespace; the dual, a real
failure inheriting a stale exit value, would have read as a false green.

The prelude now only raises; the agent stashes the value into the EXECUTING
session's globals when the exception reaches it, because the agent is the only
party that knows which session ran the raising cell.

## The runtime a notebook actually gets

Four pieces of what a Fabric notebook takes for granted, now provided instead
of worked around:

- **`/lakehouse/default/Files`.** The control plane posts `/mount` at session
  bind and the agent mirrors the bound lakehouse's `Files/` tree from OneLake.
  Contract files and config reach the runtime the way they do on Fabric:
  upload them to the lakehouse, the mount does the rest. Divergences from the
  FUSE mount are documented in the module: one-way read-only, sync-at-bind,
  one mount point. The mirror is independent of session call order, so the
  first run after an agent restart gets it too, and a mount that could not
  happen is logged at bind time instead of surfacing later as a
  FileNotFoundError deep inside a notebook.
- **`import notebookutils`.** The package the image ships is now importable
  inside executed notebooks, so frameworks that resolve workspace context
  through it stop falling back or raising.
- **Custom libraries.** Wheels placed under `/opt/wheels` (a compose overlay
  mount) install at agent startup, which is mechanically how a Fabric
  Environment item delivers custom libraries. The emulator knows no package
  names; consumers ship what they ship.
- **A storage token that outlives an hour.** The sail launcher is now a
  supervisor: it re-mints the Storage token shortly before expiry and restarts
  sail with the fresh one, instead of the old single mint whose expiry
  surfaced an hour into a long run as a 401 that read like a storage outage.
  The plain-exec path survives for real-Azure and static-token use.

## The pipeline notebook activity is now the real thing

`TridentNotebook` submitted a real job before; now it behaves like Fabric's:

- The activity's `parameters` resolve against the pipeline scope (values may
  be expressions) and reach the notebook as parameter overrides, applied
  beneath the parameters cell rather than the first cell.
- With a Spark agent configured the activity is SYNCHRONOUS: it drives the run
  and succeeds or fails on the run's actual terminal state, surfacing the
  failure reason and `exitValue`. Without an agent the Pending contract is
  unchanged.
- `workspaceId` is honoured, including the zero-GUID sentinel for "this
  pipeline's workspace", so cross-workspace activities resolve and
  same-workspace Git exports work as committed.
- List and dict parameter values are refused with Fabric's own restriction
  stated, because rendering one anyway would make the emulator more permissive
  than the thing it emulates.
- The activity's output now mirrors the documented Synapse ancestor shape
  (`result.{runId, runStatus, exitCode}`), with `exitValue` emitted alongside
  `exitCode` because the sources disagree on the name and real pipelines are
  written against both.

## Sharper failure modes

- A RunNotebook job can no longer report green over a run that never ran: job
  status is reconciled against the saved run, and a failure names the cell.
- A session binding a lakehouse its workspace does not have (a stale
  deployment, or a redeploy racing the updateDefinition LRO) logs exactly
  that, instead of silently skipping catalog and mount.
- The JVM runtime image installs the python a notebook needs, so the first
  framework import fails no longer masquerades as a notebook fault.

## Tooling, CI, security

- Test coverage over the previously uncovered resolvers and escaping paths
  (PR #16), and three CI gates fixed where they failed on a runner and not on
  a laptop.
- A security policy of our own, so reports stop reaching Laminas.

## Known issues

- The JVM overlay's base image ships Python 3.8, below what current consumer
  frameworks require; the overlay also inherits an unsuitable healthcheck and
  a `SPARK_REMOTE: !reset` that does not survive an additional compose overlay
  file. Nothing in CI composes that file yet.
- The Files mirror is one-way and sync-at-bind; a notebook WRITE to
  `/lakehouse/default/Files` does not propagate back to OneLake.
- The MERGE and CTAS routes cover their bounded grammars only; DELETE clauses,
  subquery sources, and column lists in CTAS fall through to the engine, where
  Sail's own limitations still apply.
- `input_file_name()` inside a SQL string bypasses the reconstruction.
