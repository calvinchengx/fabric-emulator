# v0.18.0

Notebook orchestration is now built against Microsoft's reference rather than
against inference. Checking `notebookutils.notebook`'s documented contract
found that three of its answers were wrong in the direction that matters
least visibly: **the emulator returned something plausible, and Fabric returns
something else.** Code branching on those answers passed locally and behaved
differently in production.

One breaking change, called out first because it is the one that changes an
existing return value.

---

## Breaking: `notebookutils.notebook.run` returns the exit value

Fabric's reference is explicit — `run()` "returns the exact string passed to
`notebookutils.notebook.exit(value)` in the child notebook. If `exit()` isn't
called in the child notebook, an empty string (`""`) is returned."

This returned the terminal job **status** instead, so:

```python
rows = notebookutils.notebook.run("load_bronze")   # "3" on Fabric
if rows == "Completed":                            # only ever true here
    ...
```

A parent branching on a child's exit value took one path against the emulator
and the other against Fabric. The exit value was never missing — the engine
posts it, the service stores it, and `…/jobs/instances/{jid}/notebookRun`
serves it. Nothing asked for it.

**What to change.** A caller that wanted the status should read it from the job
instance; a caller that wanted the exit value now gets it. `timeoutSeconds=`
and `workspaceId=` keep working as keyword aliases for Fabric's
`timeout_seconds=` and `workspace=`.

## `runMultiple` raises on failure, and carries partial results

Fabric's documented pattern for a partly-failed DAG is:

```python
from notebookutils.common.exceptions import RunMultipleFailedException

try:
    results = notebookutils.notebook.runMultiple(DAG)
except RunMultipleFailedException as ex:
    results = ex.result
```

`runMultiple` returned quietly regardless, so that `except` branch never ran
locally and a caller never learned an activity failed. It now raises with the
full result dict on `.result`, and `notebookutils.common.exceptions` exists at
the import path Fabric puts it on.

## `runMultiple` results carry `exception`, Fabric's key

The documented value shape is `{"exitVal": str, "exception": err or None}`.
Ours had `exitVal`/`message`/`status`/`error` and no `exception`, so
`result["exception"]` — straight from the reference example — raised
`KeyError`. `status` and `error` remain as emulator extras for local
debugging, because Fabric's two keys cannot express "did not run because a
dependency failed" versus "ran and failed"; nothing should depend on them.

## `timeoutPerCellInSeconds` was applied as a whole-notebook deadline

It is per **cell**. A ten-cell notebook given the default 90 is allowed 900
seconds on Fabric and got 90 total here, so a legitimately slow DAG failed
locally and passed in production. The budget is now the per-cell value times
the notebook's real cell count, read from the parsed run before it finishes —
exact, not assumed.

## New: `validateDAG`, duplicate-name refusal, `workspace`

- **`validateDAG(dag)`** — a public Fabric method with no implementation here.
  Returns `True` or raises, catching duplicate activity names, dependencies
  naming an activity outside the DAG, and cycles. Same code `runMultiple`
  reaches, so the two cannot drift.
- **Duplicate activity names are refused.** Names key the results and are what
  `dependencies` point at; a repeat silently dropped one activity's result.
- **`workspace`** is Fabric's field name and takes a name *or* an id.
  `workspaceId` is accepted as an alias.
- **DAG-level `timeoutInSeconds`** is enforced, defaulting to Fabric's 12
  hours. Activities past the deadline are reported rather than dropped: a
  short result dict is indistinguishable from a DAG that never held them.

## Fixed: concurrent Livy sessions could read each other's tables

Unrelated to notebooks, found while mapping the above. The Spark agent holds
one SparkSession and serves concurrent requests, and registering a lakehouse
moved the **process-wide** current database. Two notebooks bound to different
lakehouses raced, and the loser's unqualified `spark.table("customers")`
resolved against the other lakehouse — rows, from the wrong place, with no
error.

Each Livy session now gets its own `newSession()`, which shares the engine and
splits catalog state. Engines that cannot provide one fall back to the shared
session and now **detect** the collision, reporting that the qualified name is
required instead of serving another lakehouse's data.

## Known divergences, unchanged and deliberate

- **`runMultiple` runs sequentially.** Fabric defaults `concurrency` to 3× the
  CPU count. Reproducibility is worth more than parallelism in a test harness,
  and this is recorded in `docs/parity.md` as a chosen divergence.
- Child notebooks run in isolated sessions rather than sharing the parent's.

Both are tracked in
[docs/39-run-multiple-parity-plan.md](../39-run-multiple-parity-plan.md).
