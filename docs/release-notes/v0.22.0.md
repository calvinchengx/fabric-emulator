# v0.22.0

The range starts at `571abfa` (#182), the first commit after the `v0.21.0` tag.

## Behaviour changes — read this one before upgrading

- **Spark job definition and Invoke copy job activities now run.** v0.21.0
  refused both by name, with a message stating the capability existed and only
  the wiring was missing. That wiring landed: `InvokeCopyJob` moves real bytes
  through the same executor a direct Copy job run uses, and
  `SparkJobDefinition` submits a real job and drives it to its actual outcome
  when a Spark agent is attached. With **no** engine attached the job is
  submitted and left Pending and the activity says so, rather than reporting
  success.

  **If you pinned v0.21.0 and designed around the refusal — skipping the
  activity, or marking it Inactive — those steps now execute.**

- **The notebook prelude no longer defines `notebook_exit`.** It never was a
  Fabric global. Real Fabric defines `notebookutils.notebook.exit(v)` and the
  older `mssparkutils.notebook.exit(v)`; both still work here and are unchanged.
  The bare name was ours, and every notebook written against this emulator could
  pick it up.

  **If your notebook calls `notebook_exit(...)`, it now fails locally with
  `NameError` — which is exactly what it already does on a tenant.** Replace it
  with `mssparkutils.notebook.exit(...)`. That is the whole upgrade.

  This one is worth a sentence on why, because the break is the point. A name the
  emulator *lacks* fails here, immediately, with a stack trace on the offending
  line. A name the emulator *adds* has no local symptom at all — nothing in a
  green run says anything is wrong, and the failure waits for a deployment. It
  already caught a real consumer: a silver notebook ended with a bare
  `notebook_exit(...)` and would have died at its **last line**, after reading,
  conforming, quarantining and writing every table. The work done, the tables
  there, and the run failed for a reason unrelated to the data.

  `e2e/notebook-driven` used the injected name and said in a comment that it was
  "the Fabric contract"; `docs/12` calls that harness the path a consumer with no
  clone can walk, which made it the copy-paste template for exactly the people it
  would strand. Both are corrected, `e2e/notebook-run`'s stand-in engine now
  injects the same names as the real prelude rather than a third set, and a test
  asserts no notebook this repo ships uses the bare spelling.

## Fixes found by running it

- **The clients had no retry, and real Fabric refuses a connection now and
  then.** Measured: polling a job instance every 0.3s, **1 request in 25** came
  back `[Errno 61] Connection refused`, reproducibly. Neither
  `fabric-emulator-notebookutils` nor `fabric-target` retried a refused
  connection — `fabric-target` honoured `Retry-After` on a 429, which is a
  *response*, so the service had answered — and one refusal killed a whole
  notebook run partway through. Against the emulator on loopback a refusal
  essentially never happens, so this looked perfect locally and died on a
  tenant, in the two packages we publish rather than in an example.

  Both now retry a refused connection with backoff, and honour `Retry-After`
  where the service sends one. **Deliberately narrow:** only a refused
  connection and an explicit 429/503 are retried, because those are the cases
  where the service provably did not process the request. A 500/502/504 or a
  read timeout arrives *after* the request landed, so retrying a POST could
  submit the same notebook twice — a duplicate run is worse than a surfaced
  error.

- **`notebookutils.notebook.run` gave a multi-cell notebook a one-cell deadline
  on real Fabric.** The per-cell budget is multiplied by the notebook's cell
  count, read from `…/jobs/instances/{jid}/notebookRun` — which is the
  *emulator's* endpoint. Real Fabric answers it `404 EntityNotFound`, and the
  client read that absence as **one cell**, so a twelve-cell notebook got 1/12
  of its budget and failed with a spurious timeout while the same notebook
  passed here. A cell count that cannot be read is now unknown rather than 1,
  and an unknown count uses a whole-notebook ceiling.

  The same endpoint carries the exit value, so on real Fabric `run` now returns
  **`None`** — *could not be obtained* — where it returns `""` here for a child
  that never called `exit()`. Those are different facts and the client
  collapsed them, so every run on a tenant looked like a notebook that had
  deliberately exited empty. Both are falsy: `or ""` and `or 0` fallbacks are
  unaffected. It is recorded as a declared divergence in the differential suite
  and on the parity map, and it is why contoso-data-platform returns metrics
  through a one-row Delta table.

- **OneLake has two hosts and the examples used one.** Landing bytes went to
  `{control-plane}/onelake/…`, which is the emulator's own routing spelled out,
  so it 404'd on a tenant; and a blob-shaped `PUT` aimed at the DFS host earns
  `IncorrectEndpointError: Operation not supported on the specified endpoint`.
  `delta-rs` wants `onelake.dfs`, a raw upload wants `onelake.blob`, and
  `common.py` now resolves both per target. The emulator serves both shapes on
  one surface, so nothing local distinguished them — this survived hundreds of
  green local runs before a tenant saw it.
