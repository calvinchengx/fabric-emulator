# v0.24.0

The range starts at `v0.23.0`. Three things that were true in the tree and
not in a release: **ARM-created capacities appear on `GET /v1/capacities`**,
a notebook that writes under `/lakehouse/default/Files` actually lands in
OneLake, and **capacity has a concurrent-job ceiling**.

Upgrade from v0.23.0 if you want any of those. Stay if you don't.

---

## ARM capacities, when you opt in

A Fabric capacity in Azure is an ARM resource. This process never created
one — it seeded a local row and listed that. arm-emulator now owns
`Microsoft.Fabric/capacities`, and this release **consumes** that.

Set `FABRIC_ARM_URL` (or `-arm-url`) to an arm-emulator origin that serves
`GET /_family/capacities`. Capacities created over ARM then appear on
`GET /v1/capacities` under the Fabric REST GUID ARM assigned at create. The
seeded default stays; it cannot be deleted. Empty `FABRIC_ARM_URL` is
standalone, as before — fabric-cicd does not need ARM.

The poll interval is `FABRIC_ARM_POLL_SECONDS` / `-arm-poll-seconds` (default
5; `0` means 5). A transient ARM outage leaves last-known capacities in
place.

This repo's own compose does **not** set the variable. The family BOM in
[azure-emulators](https://github.com/calvinchengx/azure-emulators) is where
it is wired against released images. `e2e/arm-capacities` is the witness:
`azure-mgmt-fabric` creates a capacity on a pinned arm-emulator (`v0.4.1`)
and this binary lists it.

## Capacity job queueing

Capacity has a concurrent-job ceiling (default 999, overridable so a test
can set it to 1). Manual submits against a full capacity are
`430 CapacityNotAvailable` with `Retry-After`. Background jobs (scheduled,
event-triggered) enter `Queued` and are admitted FIFO when a slot frees.
Same-item jobs are not serialised — two runs of one notebook both occupy
slots when capacity allows, which is the Delta collision Fabric allows.

SKU is still not consumed compute. The ceiling is a count of in-flight
jobs, not CU.

## `/lakehouse/default/Files` writes reach OneLake

A notebook that writes through the default Files mount used to succeed in
the session and leave OneLake empty: the mount was a local directory, and
nothing flushed it. Every statement now copies that tree back, so a later
read over the DFS/Blob surface sees the same bytes. That is what Fabric
does, and what a pipeline Notebook activity depends on.

## Also since v0.23.0

`dbt-fabric` 1.11 now drives the warehouse through `mssql-python` rather
than pyodbc. Windows GNU Make in CI is pinned to the versioned Chocolatey
nupkg, because searching the community index 404'd the package while the
bytes were still there.

## Upgrading

Pull `0.24.0`. Existing workspaces, items and OneLake contents are
unchanged. Nothing starts polling ARM unless you set `FABRIC_ARM_URL`. A
test that submits many jobs at once against a capacity of 1 will now see
`430` or `Queued` instead of every job running.
