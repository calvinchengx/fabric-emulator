# v0.29.0

The range starts at `8856544` (#303), the first commit after the `v0.28.0`
tag: 6 commits. Two are bugs a consumer would have hit — both found by the same
kind of work, a real dbt-fabricspark project driving this emulator — one is a
behaviour change worth reading before you upgrade, and the rest are the
witnesses that would have caught them.

**Read this one if you use dbt-fabricspark.** Silver tables built by dbt were
landing in the engine's own warehouse rather than at their stated LOCATION, and
saying they had succeeded. If you have models that dbt reports as built but the
lakehouse never shows, this is why, and upgrading fixes it — you will want to
rebuild those models so the data arrives where the SQL analytics endpoint can
see it.

---

## The CTAS matcher claimed the exceptional shapes and missed the ordinary ones

`_CTAS` decides whether the agent writes a table at the LOCATION the statement
names, or lets the engine put it wherever it likes. It required the query to
begin with `SELECT`, immediately after `AS`. Neither assumption survives contact
with dbt:

- a dbt model file conventionally **opens with a comment** saying what it is
  for, and that comment travels into the statement between `AS` and the query;
- `with … select` is the **canonical dbt model shape** — dbt's own
  documentation writes models as CTEs.

Measured on one project, eight models, split exactly by their first keyword:
the three opening with `SELECT` were intercepted and landed in OneLake with a
`_delta_log`; the five opening with `WITH` fell through to the engine, which
honoured the LOCATION and wrote **bare zstd parquet** there instead. A directory
of parquet with no Delta log is not a table the lakehouse can read, so
`refreshMetadata` did not even enumerate those five.

dbt reported `OK created sql table model` for all eight.

That is the shape of the failure worth naming: the tables are real, queryable
from Spark, and simply not where the statement said. The lakehouse never
discovers them, its SQL analytics endpoint never reflects them, and the next
layer's every `source()` fails to resolve — pointing at the layer that is fine.
Between the two misses, the shapes that *did* work were the exceptions.

**`CREATE OR REPLACE` now replaces the schema too.** Once the above is fixed,
an overwrite whose columns differ from what is already at the location fails
with `Field 'x' not found in table schema. Use mergeSchema=true`. A model that
gains or loses a column therefore builds once and fails on every run after —
which is a normal day in dbt. Set for REPLACE only: a plain CREATE over an
existing table is already refused, and widening its schema silently would be
the opposite of what it asked for.

The three contract rows are copied **verbatim from a dbt-fabricspark debug
log**, whitespace and backquoted relation included. Every hand-written probe of
these shapes passed; only the adapter's own output failed, so a tidied row
would have proved nothing.

## A SQL result carrying a date no longer drops the connection

`run_sql` built its rows with `list(r)` and handed them to `json.dumps`
untouched. Any result carrying a DATE — `SELECT current_date()`, or a
`to_date()` cast over a bronze column — raised

```
TypeError: Object of type date is not JSON serializable
```

*inside* the handler, so the reply was never written. The caller saw only
`RemoteDisconnected`, which reads as a network fault: reported from the field as
first-suspected OOM, then a timeout, while the agent sat at 176 MiB of 15.7 GiB
and `run_sql` had already succeeded. Any dbt model returning a bare date killed
the agent, and dates are not exotic in a warehouse.

Decimal becomes a string rather than a float — a warehouse decimal that
silently loses precision on the way out is a wrong answer, which is worse than
an error. The declared type still reaches the client in the envelope's schema.

Encoding moved to `httpjson.encode_response`, which answers 500
`ResponseNotSerializable` **by name**. That is a backstop, not the fix:
stringifying everything there would hide the next gap exactly as this one was
hidden.

## A run whose Environment was not applied now fails

#299 made a notebook apply its bound Environment. Applying stayed
fire-and-forget, so an Environment that could not be read, or that the agent
declined — most realistically because another session already holds a different
one, which this emulator cannot isolate per container — left the run finishing
**Completed** with the run detail still listing the Environment it had not
honoured.

Resolved, reported, ignored is worse than unimplemented, because the metadata
says the dependency was met. Such a run now fails.

## The witnesses that would have caught them

The dbt-fabricspark suite could not have caught the date crash: `stg_countries`
returns two strings, and a table model is `create table as select` — no rows
come back over the wire at all. It proved DDL and a count, and nothing about the
values.

`silver_fx_daily` was added because its result is two DATE columns and a
`decimal(19,6)` from a model whose reason to exist has nothing to do with types
— much closer to how this reaches a user than a model written to return a date.
`dbt show` joins as a stage because it is the one that carries values *back*.

Running it found a **second copy of the same bug**: the suite runs its own
`e2e/dbt-fabricspark/sql_agent.py`, which had the same two row-building sites
and the same bare `json.dumps`, so it still crashed after the agent was fixed.
It now imports the agent's own encoder rather than carrying a copy — keeping a
second implementation is exactly how one fix missed the other.

## Dependencies

`sqlparse` moves to 0.6.0, over dbt-core's `<0.6.0` upper bound. Four
advisories patch in 0.6.0 and every published dbt-core forbids it, so no
ordinary upgrade reaches it; dbt's one call site returns byte-identical SQL
under both.
