# v0.41.1

The range starts at `b0d1de57` (#688), the first commit after the `v0.41.0`
tag. It is a patch release, and its headline is a bug the release before it
shipped: **the engine's `count()` was wrong**, and one consumer found it first.

Two other things ride along. Every Go module now declares **1.27.3**, the patch
that carries the fix for GO-2026-6809. And the attribution gate stops refusing a
**dependency bot's** trailer, which is a fact about who opened a pull request
rather than a claim on the change.

**Read Upgrading before you bump.** Nothing here changes an API, but the engine
version does move, and a pin that disagrees with the image is a refusal rather
than a warning.

---

## The engine counted 180 rows and said 132 (#702)

`pysail 0.7.2` returns a wrong `count()` for a plan that joins a grouped
aggregate back to its source. Measured on the fixture that hit it, same client
(`pyspark-client 4.2.0`), same code:

| | |
|---|---|
| `fx_daily.count()` | **132** |
| `len(fx_daily.collect())` | 180 |
| the parquet table it wrote | 180 |

The data was never wrong. The number reported about it was — and it reached a
consumer before it reached us: `fabric-platform-notebook-pipelines` went red on

```
silver_fx_daily 132 != fx_currencies 4 * fx_calendar_days 45 (= 180)
```

That is the worst shape of engine defect. It does not crash, it does not fail a
test, and it only surfaces where one number is compared to another — which is
exactly what a consumer's acceptance suite does, and why it was theirs to find
and not ours.

**Bisected, not guessed.** The same fixture and client against three engines:
0.7.0 and 0.7.1 both answer 180, 0.7.2 answers 132. `repartition(4).count()` on
0.7.2 also answers 180, which is what rules out the data and points at the
count() rewrite. `v0.40.0` shipped 0.7.1 and passed; `v0.41.0` shipped 0.7.2 and
did not.

**The pin goes back to 0.7.1**, and `e2e/sail/driver.py` now asserts
`count() == len(collect())` on every engine. The shape is the test: a flat
`count()` passes and proves nothing, so the probe builds the one that breaks —
`distinct()` under a cross join, a non-equi join, a `groupBy`, then an equi join
back to the same source.

The engine matrix moves with it: 0.7.2 reworded its refusal for a format it
cannot read (`No data source found for: kafka`), and two cells were regenerated
under it.

## Every Go module declares 1.27.3 (#701)

GO-2026-6809 is a standard-library advisory fixed in 1.27.3, and `govulncheck`
reports it against anything older. Every workflow reads the toolchain from
`go.mod` (`go-version-file`), so the directive is the only place the version is
written: moving it moves the build, the scan and the image together.

The modules that had fallen behind were `azure-apim-emulator` (1.26.6, fixed on
main before this), `fabric-emulator` (1.26.10), `snowflake-emulator`'s e2e SDK
client (1.26.6), `go-pduckdb` (1.24.2, with two Dockerfiles and a compatibility
table to match) and `sqlglot-go` (1.26). Everything else already declared it.

`golangci-lint` moves to 2.14 with it: a binary built with an older Go refuses a
module that declares a newer one, which is how the lint job failed in its first
seconds with nothing to report.

## A dependency bot is not a co-author (#700)

GitHub appends a `Co-authored-by:` trailer for a pull request's commit authors
whenever a squash merge is made by someone else, so **every Dependabot update
lands with one**. The gate refused all of them.

The rule it enforces is about *attribution of authorship* — an assistant
claiming a share of the change. `dependabot[bot]` and `renovate[bot]` are
allowed now; everything else still fails, including a human co-author, because
the rule is one author per commit. The `[bot]` marker is required, so a bare
`dependabot <…>` is still refused.

## Upgrading

- **The engine is 0.7.1.** If you pin `pysail` yourself, pin it there too; a
  stack that mixes 0.7.2 with this image is comparing two engines.
- **Nothing else changes shape.** No route, no response, no schema.

## What this release does not fix

`fabric-platform-airflow3`'s nightly failed on `gold.fct_orders_run` on 29 Oct
with no error text captured. It is not explained by the engine pin — the same
release passed a dispatch on 28 Oct — and it is being investigated separately.
